# WebAuthn member-key vectors

ADR-0018's suite for the `webauthn:es256:` member-key kind, plus the
`ed25519:` controls that go through the same `ParseMemberKey` / `VerifyBody`
entry point. These are **verify-only** fixtures: a consumer parses the key,
runs its verifier and compares the verdict. It does not re-mint the
signatures. void-which-binds-go mints them deterministically (counting P-256
scalars, RFC 6979 ECDSA) and checks that the files equal its generator.

Generated by `go test ./identity -run TestWebAuthnVectors -update`, and
replayed by `TestWebAuthnVectorVerdicts`. All keys are test-only.

## Schema

One file per case, `<case>.json`:

```jsonc
{
  "name":        "ok-device-bound",              // == file stem
  "description": "…",
  "key":         "webauthn:es256:04…",          // the member-key string
  "domain":      "void-which-binds.delegation", // D, absent for key-string and spec cases
  "body":        "<hex>",                        // B, likewise absent
  "challenge":   "<hex>",                        // see below
  "segment":     "<base64url>",                  // the token's signature segment
  "policy":      { "rps": [ { "rp_id": "broker.example", "origins": ["https://broker.example"] } ],
                   "allow_synced": false },
  "expect":      "ok",                           // or an ADR-0018 refusal word
  "signature_valid": true                        // spec cases only
}
```

- **`segment`** is exactly what follows the `.` in a token. For a `webauthn:`
  key it is `base64url` of the envelope
  `{"ad":<b64url authenticatorData>,"cd":<b64url clientDataJSON>,"sig":<b64url DER>}`.
  For an `ed25519:` key it is `base64url` of the raw 64-byte signature. All
  base64url is unpadded.
- **`challenge`**. When `domain` is present and the key is `webauthn:`, it is
  `SHA-256("void-which-binds/webauthn/challenge/v1" ‖ 0x00 ‖ D ‖ 0x00 ‖ B)`, a
  known answer for the derivation, and the verifier derives it from `domain`
  and `body` itself. When `domain` is absent (the `spec-*` cases), it is the raw
  challenge the assertion is verified against.
- **Key-string cases** (`key-*`) have only `key` and `expect: "malformed"`.
  Parsing the key must fail.
- **`expect`** is one of `ok`, `malformed`, `wrong_ceremony`,
  `challenge_mismatch`, `origin_not_allowed`, `rp_id_mismatch`,
  `user_not_present`, `user_not_verified`, `synced_not_allowed` or
  `bad_signature`. Every case has exactly one defect, so the verdict does not
  depend on the order of the checks.
- **`signature_valid`** asserts that the ES256 signature over
  `authData ‖ SHA-256(clientDataJSON)` verifies on its own, whatever `expect`
  says.

## Mapping beyond ADR-0018's table

ADR-0018 names the refusal words. These cases pin the rules it left to the
implementation:

- `cross-origin-true` and `top-origin-present` → `origin_not_allowed`.
- `der-trailing-bytes` and `der-not-der` → `bad_signature`. A signature that is
  not strict DER does not verify.
- **Envelope.** A segment that is not a JSON object at all is the other
  scheme's signature → `bad_signature` (`scheme-webauthn-issuer-bare-signature`).
  A JSON object that breaks the envelope rules is `malformed`. The rules are
  exactly `ad`, `cd` and `sig`, no duplicate keys, string values, unpadded
  base64url, and non-empty (`envelope-*`).
- **clientDataJSON** may carry members beyond `type`, `challenge`, `origin`,
  `crossOrigin` and `topOrigin` (browsers add some), and they are ignored. A
  duplicate key at any depth, invalid UTF-8, trailing data, a missing or
  non-string `type`, `challenge` or `origin`, and a non-boolean `crossOrigin`
  are all `malformed`.
- Every structural check runs before the semantic ones: the envelope, then
  clientDataJSON, then the authenticatorData layout (at least 37 bytes, AT
  clear, and trailing bytes only when ED is set). The semantic checks then run
  in §7.2 order, with the signature last.

## The spec cases

The two `spec-*` cases are the authentication halves of WebAuthn L3 §16
vectors, copied verbatim (RP ID `example.org`, origin `https://example.org`).
The key is derived from the spec's `credential_private_key`, and
`internal/webauthntest` checks that this matches the spec's COSE key and that
RFC 6979 signing reproduces the spec's signature byte for byte.

- `spec-16.2-authentication` is the case ADR-0018 names. The spec's
  authenticatorData flags are `0x19` (UP, BE, BS), so UV is clear. Under
  ADR-0018, which always requires UV, it is refused `user_not_verified` after
  steps 10–16 pass. `signature_valid: true` pins steps 20–21 separately.
- `spec-16.6-authentication` is added so that independent spec bytes pass every
  check from 10 to 21. Its flags are `0x0d` (UP, UV, BE), so it is `ok` with
  `allow_synced: true`.
